# Cortex Bridge v0.5.0 Product and Technical Design

**Status:** Approved for implementation  
**Date:** 2026-07-26  
**Target release:** v0.5.0

## Objective

Ship Cortex Bridge v0.5.0 as a trustworthy local application that lets a
person continue a ChatGPT conversation or explicitly delegate work to a local
executor without confusing those two actions.

The release is complete only when:

- local execution fails closed and never reports success without independent
  evidence;
- two conversations can be active without sharing drafts, events, browser
  sessions, mission state, or delivery proofs;
- the French interface is understandable without reading technical logs;
- a cached conversation opens immediately and every live switch either
  succeeds within 10 seconds or ends with a recoverable error;
- human and agent-assisted installation flows are reproducible and require
  explicit consent before installing third-party software;
- the public repository is entirely documented in English;
- the release includes anonymized visual guides, an animated architecture
  diagram, and machine-readable verification evidence.

## Supported product shape

v0.5.0 is a local-first macOS application served on `127.0.0.1`. It uses the
person's existing authenticated ChatGPT browser session through the packaged Chrome extension.
It does not call private ChatGPT APIs, bypass login challenges, or silently
send messages.

The initial public support target is:

- macOS;
- Python 3.11 or newer;
- Node.js 20 or newer for frontend development and rebuilds;
- Google Chrome 116 or newer with the packaged Cortex Bridge extension;
- ChatGPT access supplied and authenticated by the user;
- Ollama only when a local-model executor is explicitly selected.

Linux and Windows remain unsupported for v0.5.0 unless their full install and
acceptance matrices pass before release.

## Product model

### One composer, two explicit outcomes

Cortex Bridge must not expose persistent "Chat" and "Mission" modes.

- `Send` posts the exact draft to ChatGPT.
- `Execute on this computer...` opens a preflight review.
- Pressing Enter always performs `Send`.
- Attaching a file or taking a screenshot never starts a local execution.
- Intent classification may suggest preparing an execution. It must never
  convert a send into an execution or grant permission.

The execution preflight displays:

- the target conversation;
- the exact workspace;
- read, write, process, network, and deletion capabilities;
- the selected executor and whether it is deterministic or model-driven;
- maximum iterations and duration;
- attached files that will be made available;
- actions that require approval.

The final action is named according to its effect:

- `Start read-only execution`;
- `Start with write approvals`;
- `Start with reviewed process commands`.

An execution is attached to a normal conversation. It is not a separate
conversation type and does not create a second navigation hierarchy.

### Truthful executor roles

The UI and documentation must describe only code paths that are actually
used:

- `Deterministic tool runner` means the bridge executes validated tool calls
  without a local LLM.
- `Ollama executor` means the selected Ollama model was called and its model
  name and digest are present in the audit record.
- simulation and demo results are never accepted by release tests.

If the Ollama execution path is not proven by the release gate, it remains
labelled experimental and cannot be the default.

## Information architecture

### Conversation sidebar

The expanded sidebar contains:

1. `New conversation`;
2. search;
3. `Pinned`;
4. `Projects`, grouped by real project title and hidden when empty;
5. `Recent`;
6. archived conversations and refresh in a secondary menu;
7. settings at the bottom.

Rules:

- load at most the latest 50 conversations;
- never duplicate a conversation across sections;
- remove conversations that no longer exist in ChatGPT after reconciliation;
- update title, pin, project, preview, and timestamp changes;
- show a message count only when it is known from a cached snapshot;
- hide unknown counts instead of displaying "Not synchronized";
- the collapsed rail exposes only conversation navigation, new conversation,
  expand, and settings.

### Conversation header

Two independent status controls stay visible at 375, 768, and 1440 pixels:

- `ChatGPT`: connected, synchronizing, blocked, or disconnected;
- `Local agent`: ready, working, paused, awaiting approval, or unavailable.

The header also contains:

- conversation title and category;
- `Open in ChatGPT`;
- `Activity and health`;
- latency only when a measured value exists.

The ChatGPT status is derived from transport health. The local-agent status is
derived from the selected executor and current execution state. Neither may
reuse the other subsystem's aggregate status.

### Conversation body

Messages remain the dominant surface. Execution details appear in the same
chronology and collapse to one status row by default.

The send lifecycle is explicit:

1. `Queued locally`;
2. `Sending to ChatGPT`;
3. `Visible in ChatGPT`;
4. `Waiting for a response`;
5. `Response received`;
6. `Delivery uncertain` or `Failed`.

An uncertain delivery never triggers an automatic resend.

### Settings

The settings hierarchy is:

1. General;
2. AI and models;
3. Connections and permissions;
4. Advanced: runtime, storage, diagnostics, and information.

Conversation-specific controls stay near the composer:

- workspace;
- execution preflight;
- attachment and screenshot actions.

Raw protocol JSON, DOM selectors, and verbose process logs stay under
Diagnostics.

## Visual direction

### Subject, audience, and job

- **Subject:** a local bridge carrying verified work between a cloud
  conversation and a computer.
- **Audience:** technical and semi-technical people who want local execution
  without learning the bridge protocol.
- **Single job:** make the next action and its consequence obvious.

### Design tokens

The visual system keeps the existing dark, technical character while removing
decorative noise and undersized copy.

- `Carbon`: `#07090B` — application background;
- `Graphite`: `#101419` — primary panels;
- `Slate`: `#1A2027` — raised controls;
- `Signal blue`: `#4F8CFF` — transport and selected navigation;
- `Proof green`: `#36C98F` — independently verified success;
- `Review amber`: `#F2B84B` — approval or user attention;
- `Fault red`: `#F06A6A` — failure and destructive stop.

Typography:

- body and controls: Inter, system fallback;
- process data and evidence: SF Mono, Cascadia Code fallback;
- minimum body size: 14 px;
- minimum metadata size: 12 px;
- line-height: at least 1.4 for readable content.

Layout:

```text
┌──────────────────┬────────────────────────────────┬───────────────┐
│ Conversations    │ ChatGPT status  Agent status   │ Activity      │
│                  ├────────────────────────────────┤ and health    │
│ Pinned           │                                │ drawer        │
│ Projects         │ Conversation and executions    │               │
│ Recent           │                                │               │
│                  ├────────────────────────────────┤               │
│ Settings         │ Attach  Workspace  Draft  Send │               │
└──────────────────┴────────────────────────────────┴───────────────┘
```

The signature element is the paired status rail: two adjacent, independently
animated lines show the verified handoff from ChatGPT to the local agent.
Motion is functional, limited to a single handoff animation and state
transitions, and disabled by `prefers-reduced-motion`.

Icon-only controls require:

- an accessible name;
- a tooltip on hover and keyboard focus;
- a 44 by 44 pixel mobile target;
- a text alternative when the action has material consequences.

Closed drawers are `inert`, `aria-hidden`, removed from tab order, closed by
Escape, and return focus to their trigger.

## Runtime safety

### Completion and command results

- a missing deterministic final validator produces a non-terminal state, not
  `COMPLETED`;
- a process with a non-zero exit code, timeout, signal, truncated critical
  output, or missing expected artifact cannot validate successfully;
- every terminal success records the validator identity and evidence.

### Filesystem and process boundaries

Direct file tools:

- accept workspace-relative paths only;
- resolve symlinks before access;
- reject traversal, absolute paths, device paths, and sensitive files;
- never delete files in v0.5.0;
- write atomically and preserve an audit hash.

Process execution:

- uses argument arrays with `shell=False`;
- removes inherited secrets from the environment;
- uses an explicit executable and subcommand policy;
- rejects inline interpreter execution such as `python -c`, `node -e`, shell
  command strings, package installation, network clients, and destructive
  commands;
- runs with the workspace as its working directory;
- always requires an explicit per-command review unless an OS-level sandbox
  proves confinement.

The documentation must not claim that an unsandboxed child process is unable
to inspect the rest of the computer. The v0.5.0 guarantee is that Cortex does
not run such a process without showing the exact command and obtaining
approval.

### Conversation concurrency

- active writer slots are keyed by canonical conversation identity;
- provisional new-conversation identities use unique UUIDs and are replaced
  atomically after ChatGPT assigns a canonical ID;
- the same conversation cannot have two writers;
- two different conversations may write concurrently only with distinct
  transport bindings;
- a third write returns HTTP 409 and preserves its draft and attachments;
- read-only browsing remains available for all conversations;
- restart recovery reconstructs writer slots from persisted non-terminal
  missions.

## Performance and transport

- render cached sidebar data without waiting for the Chrome extension;
- update conversation metadata in the background;
- switch through ChatGPT's SPA navigation first;
- stop the normal switch path at 10 seconds;
- expose an explicit `Retry with page reload` recovery action;
- poll only the selected conversation for message deltas;
- abort obsolete reads when the user selects another conversation;
- keep one event stream per active conversation or multiplex events by
  conversation ID with strict filtering.

Release budgets:

- local UI usable: less than 2 seconds;
- conversation switch p95: less than 3 seconds;
- conversation switch hard maximum: 10 seconds;
- local queued state visible: less than 200 milliseconds;
- no React hydration or browser-console errors;
- no cross-conversation state leak in ten repeated dual-writer runs.

## Attachments and screenshots

- support common document and image types accepted by ChatGPT;
- validate locally before upload;
- enforce 512 MB per file, 20 MB per image, and type-specific limits described
  in the current official documentation;
- neutralize path traversal in filenames;
- validate detected MIME type, not only the extension;
- preserve drafts and staged attachments after rejection or transport error;
- make screenshot target and crop explicit;
- record upload delivery evidence;
- clean abandoned temporary files.

Current external limits must be linked rather than copied as timeless facts.
The UI may show the current known value while treating a server rejection as
authoritative.

## Installation

### Human installer

`scripts/install.sh` performs local checks and offers component-by-component
installation. It must:

- explain why each dependency is needed;
- show the official product URL;
- show the exact command and disk/network impact;
- ask before installing or downloading each external dependency;
- never use `sudo`, log in to ChatGPT, accept terms, or install a browser
  extension on the user's behalf;
- create an isolated Python environment;
- install frontend dependencies only when a rebuild is requested;
- run `cortex doctor` and print actionable results;
- support a dry-run mode.

### Agent-assisted installer

`docs/agent-installation.md` is written for agentic LLMs. It instructs the
agent to:

1. inspect without changing the machine;
2. present a dependency manifest to the user;
3. verify every official link;
4. ask for one explicit approval covering named components and commands;
5. install only approved components;
6. stop for browser login, extension installation, license acceptance,
   privilege escalation, or secret entry;
7. run doctor and tests;
8. report exact changes and rollback commands.

The repository also contains a machine-readable
`install/dependencies.json` with:

- component;
- required or optional status;
- purpose;
- official URL;
- supported install commands;
- expected download size when known;
- data locations;
- uninstall instructions;
- whether interactive user action is mandatory.

## Documentation and privacy

The public GitHub repository is English-only for:

- README;
- installation;
- agent-assisted installation;
- architecture;
- security;
- user guide;
- troubleshooting;
- testing;
- contributing;
- changelog and release notes.

The application interface remains French by default and can later use a
translation layer.

Visual documentation uses a synthetic demo profile. No real conversation
title, account name, email, filesystem path, model history, browser profile,
or personal document may appear.

Before publication:

- remove image metadata;
- scan screenshots with OCR for personal strings;
- blur any residual identifier;
- scan the repository for user names, home paths, email addresses, secrets,
  and unrelated project names.

The in-app animated architecture diagram is a React/SVG/CSS component. The
README animation is rendered from the same diagram state model. Remotion is
kept outside the runtime and used only if the documentation renderer requires
timeline composition.

## Verification strategy

### Automated layers

1. Unit tests: protocol, validation, process policy, paths, attachments,
   state reducers, grouping, status copy.
2. Integration tests: FastAPI, SQLite, approvals, restart recovery, transport
   fixture, Ollama fixture, uploads.
3. Browser E2E: real frontend and backend with deterministic fixtures.
4. Live Chrome-extension checks: explicit, opt-in smoke matrix against ChatGPT.
5. Recovery tests: six crash injection points with no duplicate send or
   execution.
6. Soak tests: event streams, process cleanup, database consistency.

### Mini-site acceptance mission

Each run receives a fresh dedicated workspace and conversation. Cortex creates
a dependency-free local site with HTML, CSS, JavaScript, and README, starts it
on an available `127.0.0.1` port, proves HTTP and browser behavior at 375, 768,
and 1440 pixels, records screenshots, then stops the server.

An oracle outside the mission workspace verifies:

- required files and hashes;
- no external URLs or unexpected files;
- no change outside the workspace;
- no browser-console error;
- keyboard, contrast, and reduced-motion behavior;
- HTTP 200 and correct content types;
- no remaining child process;
- every process exit code equals zero;
- terminal completion references deterministic evidence.

Three fresh runs must pass consecutively. Failed attempts remain recorded and
cannot be hidden by rerunning until green.

## Release gate

v0.5.0 may be tagged only when:

- the full automated suite passes from the documented clean install;
- all P0 and P1 security and recovery tests pass;
- process failures cannot produce a successful validation;
- no terminal success exists without deterministic evidence;
- ten dual-conversation runs complete without state or message crossover;
- three mini-site acceptance runs pass consecutively;
- the frontend has zero console errors at 375, 768, and 1440 pixels;
- install dry-run, clean install, doctor, start, stop, and uninstall paths are
  verified;
- all public links return an expected successful status;
- the English documentation, anonymized screenshots, and animated diagram are
  reviewed;
- the repository contains no personal data or secrets;
- the version is consistently `0.5.0`;
- the release diff and verification report are shown before pushing or
  publishing.

## Post-release positioning decision

The launch and open-source recommendation is made only after the release gate.
It must compare current adjacent projects, assess the maintenance and security
burden of Chrome-extension automation, and propose channel-specific material for
LinkedIn, short-form video, developer communities, and GitHub.
