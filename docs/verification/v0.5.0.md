# Cortex Bridge v0.5 verification map

This file maps release-evidence counters to executable tests. The machine-readable result is `v0.5.0.json`.

## Automated suites

- `backend`: every test discovered under `tests/`.
- `frontendUnit`: Vitest component tests plus the runtime, privacy, image and build contracts.
- `e2e`: Playwright fixture tests against the shipped interface.
- `a11y`: Axe, keyboard, reduced-motion and responsive checks at 375, 768 and 1440 pixels.

## Acceptance counters

### Twenty fixture missions

`tests/test_transport_fixture.py` contains the numbered 1–20 transport contract: selection, lock, send, streaming, stable extraction, blocker states, restart, pause, cancellation, uncertain delivery and manual fallback. All twenty must pass in the same backend run.

### Ten cold dual-writer runs

`frontend/e2e/dual-conversation.spec.ts` reloads the application and repeats the complete A/B/third-writer scenario ten times. Each run proves distinct A and B sends, rejection of a third writer, and preservation of the third draft and attachment.

3. `test_playwright_driver.PlaywrightDriverTest.test_startup_failure_is_evicted_and_factory_recovers`
4. `test_transport_session_isolation.MissionPersistenceFailureTest.test_sqlite_update_failure_fails_mission_and_releases_exact_lease`

These points cover stored recovery state, surfaced server recovery, browser-start failure, database-write failure, runtime-construction failure and cancellation while browser work is still quiescing.

## Live boundary

Earlier owner-authorized runs observed one conversation, two isolated writers,
third-writer refusal, a text-file upload, an explicitly authorized screenshot,
closed-tab recovery and three mini-site missions. No account detail, private
title, conversation content or unredacted live screenshot was committed.

Those observations cannot serve as compliant release acceptance. The current
[OpenAI Europe Terms of Use](https://openai.com/policies/eu-terms-of-use/)
prohibit automatic or programmatic extraction of data or Output, which the
consumer adapter performs. Owner approval cannot lift that restriction.

As of 2026-08-15 the owner explicitly assumed that contractual risk and opted
in through the Settings → Transport control. Fresh owner-authorized runs
(neutral synthetic markers only, no personal content) re-verified the bridge
against the current source: one conversation, two isolated writers with zero
crossover, third-writer refusal, and a text-file upload. The truthful v0.5
verdict is therefore `OPT_IN_TECHNICAL_PREVIEW`: the bridge works and ships as
an opt-in preview that is not authorized by the provider, with the account
risk stated in the UI. It is not `RELEASE_CANDIDATE_READY_FOR_OWNER_APPROVAL`:
screenshot upload, the three mini-site missions and the clean macOS lifecycle
remain unobserved for this source.

## Clean macOS lifecycle

The current source has a stable isolated dry-run plan, but its exact hash has not
been approved for application. Install, `doctor`, start/stop, idempotent
reinstall and manifest-based uninstall therefore remain `NOT_RUN` for this
source commit. Earlier lifecycle results cannot attest this commit. The normal
plan does not use `sudo` or download Playwright Chromium, and private temporary
paths or logs are never committed.

## Commit convention

The `commit` field in `v0.5.0.json` identifies the audited source commit. The manifest may be committed immediately afterward because a file cannot contain the hash of the commit that contains itself. A release tag should include both by pointing to the evidence commit whose first parent is the audited source commit.
