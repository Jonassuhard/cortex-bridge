# Cortex Bridge v0.5 viability plan

Date: 2026-09-08. Candidate: `0.5.4`, branch `codex/v054-storage-consolidation`, analysis baseline `66741e9`.

## Objective and release definition

A person can install Cortex, connect their own ChatGPT tab in their existing Chrome profile, discuss and request local work, approve that work, inspect the real result, stop it and resume safely. The interface must report the actual browser, executor, workspace and delivery state. The product path remains ChatGPT web plus the local Chrome extension and executor.

Completion means every mandatory acceptance case below passes on the same reviewed release candidate, with no unresolved critical or major defect. It does not mean a promise of zero possible bugs. A fixture PASS does not establish a live-user PASS. A failed live case cannot become PASS because an error is now clearly displayed.

macOS is the current delivery target. On 2026-09-08 the owner explicitly deferred Windows verification and authorized continuation of the remaining plan. RE06 is retained as deferred work, not a blocker for this macOS delivery. Inventory, implementation, Windows CI and native user acceptance are still required before any Windows support claim.

## Evidence and publication rules

Every result records case ID, source commit or exact uncommitted diff hash, environment, command/actions, outcome, duration where relevant, and a link/hash for the log, screenshot or produced file. Retry history remains visible. Screenshots alone do not prove file delivery, code execution or process cleanup.

Keep private raw evidence outside public Git. Use synthetic fixtures and screenshots for the public illustrated guide. Publication is a separate stage after the selected candidate passes its required cases; previous publication authorizations do not justify calling an unfinished candidate stable.

No mount password, CAPTCHA or macOS permission is fabricated. A genuine need for user interaction blocks only that live case, not independent code work. No OpenAI API transport replaces the user's requested Chrome flow.

## Task 1: Complete the installed startup chain

One implementation owner must complete the installed startup chain with these five linked deliverables:

Confirmed prerequisite: the compiled production broker remains a protocol shell. The native owner must first implement the missing S3 authentication/codec/descriptor/self-identity/boot/envelope/cursor/start-capability behavior against the frozen S3 contract. Merely emitting STARTED, publishing the shell, or invoking the legacy one-shot route cannot satisfy the installation acceptance. Native effects remain synthetic/injected during this code tranche; real Keychain or DiskImages mutation is not authorized here.

1. Publish a complete immutable generation with installed Python, fixed entrypoint, scripts/extension and verified native helpers; selector replacement happens last and rollback preserves the previous complete generation.
2. Implement the stable native bootstrap: acquire install-shared, attest selector/generation/manifest/interpreter through retained descriptors, sanitize environment, execute only the installed entrypoint.
3. Adopt the retained install lock, acquire storage/admission in order and construct one InstalledStorageRuntime; keep helper descriptors alive until the owner releases its locks.
4. Implement managed server spawn, durable consumed lease receipt, ACK, actual STARTING/READY/CLOSED lifecycle and cleanup of only the proven owned process.
5. Prove install/start/status/doctor/stop/reinstall/uninstall when the checkout is inaccessible, including successful construction and crash/tamper/no-marker/required-storage failures.

This tranche is development work that can begin with fixtures even while the legacy image remains inaccessible. It is not complete in this pass. No fresh release, real installed startup, real ChatGPT acceptance or Windows support is claimed.

Execution boundary: one Sol implementation owner covers this coupled unit, with a Terra read-only review. Two independent Terra diagnostics may run alongside it (installed Swift/SDK selection and browser defect mapping); neither edits the implementation owner's files. No recursive delegation or Astra worker. Preserve the existing dirty tree. Do not modify the live installation, legacy image, credentials, system toolchain selection, or publish a release during this source/test tranche. Repository commits are held for integration review; partial implementation never closes the installed-startup acceptance cases.

## Task 2: Bound conversation snapshot acquisition and preserve cached content

This independent repair follows Task 5 of the existing runtime UI/browser plan. It does not depend on the unfinished installed-storage factory and does not establish live CH06/CH07 acceptance by itself.

- One Terra implementation owner covers only `console/chat.py`, `transport/chatgpt_web/adapter.py`, `frontend/hooks/useConversationController.ts`, `frontend/lib/conversation-state.ts` and their focused tests (`tests/test_transport_fixture.py`, `tests/test_transport_session_isolation.py`, `frontend/hooks/useConversationController.test.tsx`).
- Define `TRANSPORT_SNAPSHOT_BUDGET_SECONDS = 8.0`. Start one monotonic deadline at snapshot-route entry, including lock acquisition, selection, snapshot reads and the one bounded recovery. Every awaited driver operation receives the remaining budget; cancellation or recovery never resets it.
- Preserve read-only conversation isolation. A timed-out operation must release resources without a later retarget or result commit. Return `SNAPSHOT_ACQUISITION_TIMEOUT` as a retryable failure; never convert elapsed timeout into success.
- The existing UI deadline remains 10 seconds. Cached B renders immediately, remains visible after timeout, stops loading and becomes stale with one retry; late A or B responses cannot overwrite the selected conversation. Keep one refresh per epoch and the existing abort signal path. Add only the required typed trace events, not another polling loop.
- Write and run RED tests for budget consumption across selection/read/recovery, lock waiting, lock release on timeout, cached B timeout, and superseded late results. Run the complete three-file selection GREEN, typecheck and diff checks with pinned tools and isolated temporary runtime state.
- No tab retirement, installed-runtime files, effects/intent changes, browser profile, ChatGPT message, persistent/product server, production build or generated frontend output in this task. The complete Python test modules may use their existing disposable loopback HTTP fixtures, sequentially and only after coordination with the runtime worker; no real Chrome or external provider action. Tab provenance is a later distinct correction.
- Preserve the reviewed diagnostic/UI patches and all pre-existing dirty files. Do not commit or publish before integration review. Return exact hashes, commands, test output and remaining live limitations.

Review-driven scope extension: cancelled acquisition may leave an extension command in flight after its Python request expires. The current release acknowledgement does not prove quiescence, and the driver marks itself closed even if release fails. The same writer therefore also owns `transport/browser_chrome_extension.py`, `tests/test_chrome_extension_driver.py`, `chrome-extension/service-worker-core.js` and `chrome-extension/tests/extension.test.mjs` for a bounded, retryable per-session release barrier. `service-worker.js` is permitted only if its context wiring requires it. Tests must prove no premature release acknowledgement, no late reused-session retarget, no new candidate while cleanup is unconfirmed, and independent progress of two sessions. No automatic tab retirement or personal-tab closure is included; the full provenance/retirement task remains separate.
