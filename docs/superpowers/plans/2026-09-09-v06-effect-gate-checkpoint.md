# Durable approval and STOP coordinator — staged checkpoint

Implements a portion of Task 2 in [the approved durable-effects plan](2026-09-02-v054-durable-effects-and-executor.md). Full runtime activation is not enabled.

## Implemented
- Store.transaction_immediate holds the instance lock through commit/rollback and refuses nested transactions. Store.schema_version reports the actual SQLite version, including legacy zero; control_row and effect_rows refuse legacy schemas and never migrate implicitly.
- console/effect_gate.py adds exact mission challenges/responses/receipts and canonical operation-bound JSON digests. UUID identities, lowercase hex digests, 43-character Base64URL nonces and strict boolean decisions are checked.
- A pending request can be re-read without a new nonce. Changing its tuple or replaying a consumed response fails. Delayed action A responses cannot authorize action B.
- request_stop increments the durable epoch and invalidates unconsumed pending/approved authorizations. settle_stop waits for active effects. Unknown outcomes block reset even when no effect remains active. reset requires the exact current epoch and quiescent state.
- StopStatus has the approved camelCase public projection, but no HTTP route uses the new gate yet.
- Mission-tool activation validates the current decision, action, operation, payload digest, category and epoch. Approval consumption and active-effect insertion share one transaction; failed insertion rolls back consumption. Concurrent attempts for the same action produce one effect.
- Opaque, instance-bound activation objects authorize one terminal receipt. An already activated effect may settle after STOP; an effect cannot start after STOP or overwrite a terminal outcome. Receipts record trusted caller observations, not an independent filesystem verification.
- Context source digests now include schema version and, on v3, control state plus mission-scoped effects. STOP and effects invalidate old context, while effects in an unrelated mission do not.
- Ownership persistence requires an active capability. Ordinary identity records are immutable (exact retries are allowed). Only the two fixed blocked-worker tuples accept pre-activation ownership, once, with strict PID/group/start-time fields and `released=false`. The activated transition to `released=true` preserves the identity and cannot be reversed. These methods persist runner observations; they do not attest OS identities or release an actual process themselves.
- `approval_receipt` reads the exact mission/action/epoch/digest tuple from SQLite. Pending, invalidated, stale or already effect-consumed rows cannot authorize execution; denied receipts remain denied. Lookup is non-consuming and activation must independently recheck the same evidence atomically. Reconstructing a gate does not lose the durable decision.
