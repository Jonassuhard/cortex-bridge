# Cortex Bridge 0.6 — approved product direction

Status: implementation in progress; not a released or accepted version.
Authority: owner approved the ten-part 0.6 roadmap and explicitly requested execution in this conversation. This document records that scope; it is not a signature, release approval or provider consent.

## Outcome
A new user connects ChatGPT in their existing Chrome profile, connects a supported execution harness, selects an authorized workspace, and completes a verified first mission in under ten minutes excluding exceptional downloads. This threshold must be measured, not presumed.

## Product boundaries
- Separate ChatGPT model/reflection, execution harness and executor model.
- Model and reflection choices must come from fresh observed capabilities. Never invent a universal intelligence slider, bypass quotas, silently switch models or replace the requested web flow with an API.
- Two writing conversations maximum; third draft retained, no browser side effect.
- 50 most recent conversations at most; pinned/project/recent groups reflect confirmed source observations.
- One composer; clear action intent may route to execution but never grants sensitive permissions.
- Compact UI: conversation first, two truthful status indicators, diagnostics behind a button.
- Consent precedes dependencies, provider changes, cost changes and sensitive actions.
- Local and provider quota limits remain explicit. No guaranteed equivalence to Codex Astra.
- No personal paths, secrets or account data in public documentation and screenshots.
- Preserve previous version evidence and existing uncommitted changes.
- Windows live acceptance remains owner-deferred; do not advertise verified Windows support.

## Continuity contract
Transfer explicit goals, constraints, decisions and useful justifications, relevant file versions, authorized scope, confirmed effects, unresolved effects and next action. Do not export hidden chain of thought. A model summary is a claim, not a verified effect.
Changing executor requires a paused mission, no running or ambiguous effects, fresh target capabilities and unchanged workspace scope. A different provider/data recipient or cost class requires explicit user confirmation. Transport ambiguity is never retried automatically.
Durable checkpoints must be versioned, transactionally bound to the mission and verified before resume. File changes since checkpoint require reconciliation. No claim of exactly-once external effects without evidence.

## Release gates
All supported adapters pass the same acceptance suite with actual artifact inspection. First-use timing requires observed new users, not an agent impersonating them. One/two/third conversation tests, attachments, simple/sorting/site/bugfix tasks, STOP and transition failure tests are required. Missing proof remains UNCLEAR, never averaged away. Public release and GitHub publication remain a separate owner-approved step.
